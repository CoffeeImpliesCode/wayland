# Seat/Input Breadth — wlroots/smithay features we lack entirely

Scope: our input surface (`src/compositor/seat.zig`, `src/compositor/xkb.zig`, `src/backend/backend.zig` InputDevice, `src/backend/libinput.zig`, `src/server/raylib_input.zig`, synth input in `src/server/main.zig`, cursor rendering in `src/server/main.zig`) vs the full input surface of wlroots 0.20.2 (`~/projects/freedesktop-wlroots-wlroots`) and smithay v0.7.0 (`~/projects/github-Smithay-smithay`). Parity per function was covered in note 106 (seat/xkb) and 108 (data-device); this note is the BREADTH inventory: whole input features, protocols and backend paths the references have and we do not. Verdicts are for a canvas-first compositor (notes/canvas-compositing.md, zig-compositor-lib-spec.md).

## Gaps

1. **No touch at all.** `get_touch` returns a dead object (seat.zig:395-405) and libinput touch devices are not announced (`kindForDevice` in libinput.zig). wlroots has a full seat touch path (wlr_seat_touch.c, touch points, grabs, wlr_seat.h:625-691); smithay adds shape/orientation and frame dedup. A canvas compositor's core interaction — direct manipulation — is impossible without it. The task prompt confirms touch was deliberately unannounced; the breadth question is whether to keep it that way.
2. **No gesture path end to end.** libinput GESTURE_SWIPE/PINCH/HOLD events are logged as unhandled in libinput.zig's dispatch; there is no wl_pointer gesture event API and no wp_pointer_gestures_v1 global (wlroots sends them via wlr_pointer_gestures_v1.c from backend/libinput/pointer.c:187-246; smithay routes them through PointerHandle::gesture_*). Pinch-to-zoom — explicitly identified in canvas-compositing.md §4 as the natural canvas zoom control — is unreachable.
3. **No relative pointer.** Clients cannot receive unaccelerated pointer deltas (wlr_relative_pointer_v1.c; smithay PointerTarget::relative_motion). Canvas pan-with-inertia, camera drag and game-style control all need raw deltas; canvas-compositing.md §4 specifies deltas must be scaled by 1/z under zoom.
4. **No pointer constraints.** No locked/confined pointer (wlr_pointer_constraints_v1.c; smithay pointer_constraints.rs). Locked pointer is how a canvas client implements grab-to-orbit or infinite drag; confined pointer clamps to a surface region. Both depend on the missing seat grab mechanism (gap in note 106).
5. **No virtual devices, so test automation is in-process only.** The only synthesis is the hardcoded click+key in main.zig:723-730. wlroots' zwp_virtual_keyboard_v1/zwp_virtual_pointer_v1 (and smithay's virtual_keyboard) let external tools (wtype, weston-debug) drive real clients through the socket — the natural harness for the VM E2E setup the project already uses (scripts/vm-e2e.sh, uinput-devices.py).
6. **No key repeat.** repeat_info(0,0) is advertised (seat.zig:369-372), so no client ever sees repeated keys: text entry is effectively broken for holding a key. wlroots defaults rate 25/delay 600 (types/wlr_keyboard.c:140-141) and smithay configures per-keyboard repeat (keyboard/mod.rs:1320-1335). Small, high-value.
7. **No idle surface.** Neither ext-idle-notify-v1 nor zwp_idle_inhibit_v1 exist in ours; the old wlr_idle is gone from wlroots 0.20.2, so the current reference surface is exactly those two. Without them the compositor cannot coordinate blanking/DPMS, and clients cannot dim or hide their UI on inactivity.
8. **No cursor management.** The compositor draws a grey square fallback or the client cursor surface (main.zig:918-954). wlroots' wlr_xcursor_manager + wp_cursor_shape_v1 (and smithay cursor_shape.rs) give real theme cursors. For a canvas with tool states (pen/pan/zoom), compositor-side cursors are genuinely useful, not just polish.
9. **No input-device removal.** The libinput backend tracks removal internally (onDeviceRemoved) but the Backend only has `new_input` (backend.zig:29); hot-unplug leaves the compositor unaware. wlroots has `events.destroy` per device; smithay has `InputEvent::DeviceRemoved`.
10. **No input method / text input.** zwp_input_method_v2 + zwp_text_input_v3 (both references) are absent. Low priority for a canvas-first target, but text-heavy clients (notes apps!) will eventually want at least text_input_v3 for IME.

## Verdict

wlroots 0.20.2 and smithay 0.7.0 both ship a complete input stack — touch, tablet v2, gestures, relative pointer, constraints, virtual devices, idle, IME, primary selection, cursor management, device registry — of which we currently implement only keyboard + pointer basics. For a canvas-first compositor the high-value additions are: **touch** (direct manipulation is the canvas's native interaction), **tablet v2 tools** (stylus pressure/tilt is what a drawing/annotation canvas exists to host), **pointer gestures** (pinch-to-zoom, explicitly designed in canvas-compositing.md §4), **relative pointer** (raw deltas for pan/inertia, scaled by 1/z), **virtual keyboard + virtual pointer** (external test automation for the existing VM E2E harness), **keyboard repeat** (cheap, and text entry is broken without it), and the **seat grab mechanism** as the enabling layer for constraints and DnD. Optional: pointer constraints (locked, for orbit-style camera control), idle notify/inhibit, primary selection, xcursor manager (compositor tool cursors), device removal events. Out of scope for now: switch devices and keyboard groups (hardware we do not target), input-inhibit (neither reference implements it), and IME (text_input_v3 only when real text workflows demand it). smithay's lack of virtual-pointer support is evidence that even mature compositors skip parts of this surface; the canvas set above is the coherent minimum.
