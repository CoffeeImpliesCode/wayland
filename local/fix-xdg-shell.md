# fix-xdg-shell — xdg-shell area

Fix plan derived from local://cmp-xdg-shell.md, every O: citation re-verified against src/shell/xdg.zig and the reference trees (wlroots 0.20.2, smithay v0.7.0, KWin master) on 2026-08-11.

### X01 ack_configure error interface [MINOR] → ACCEPT — Reason: deliberate, spec-literal. XML xdg-shell.xml:573-574 and :592-593 mandate `invalid_serial` on the xdg_surface for acked-but-never-sent / superseded serials; ours posts exactly that on `xdg.resource` (src/shell/xdg.zig:389, :393, inside ackConfigure at :381-396). wlroots (wlr_xdg_surface.c:77-81) and smithay (handlers/surface.rs:319-322) post code-4 `invalid_surface_state` on the wm_base — same code, wrong interface per the XML. note 129 deliberately kept ours. Conformance suites keying on the wm_base interface (as wlroots/smithay generate it) will break against ours, but the XML text is on our side.

### X03 set_parent to an unmapped toplevel clears the parent [MINOR] → FIX (Phase 2)
- Files: src/shell/xdg.zig — `setToplevelParent` at :1180-1224 (unconditional `t.parent = new_parent` at :1216; self/cycle checks at :1187-1201); test `set_parent stores the parent and rejects descendant cycles (F16)` at :3561-3623. Reference: wlroots wlr_xdg_toplevel.c:193-199 (install parent only when `parent->base->surface->mapped`, else `toplevel->parent = NULL`).
- Change: after the self/cycle checks and before installing, gate on the requested parent's map state: if `new_parent != null and !new_parent.xdg_surface.surface.mapped`, treat the request as null (`new_parent = null`) — clear the old link, never store the unmapped parent, never append to its `children`. Map state is read once at set_parent time, exactly like wlroots; a later parent map requires a fresh set_parent. Keep the existing unmap-reparenting in `resetOnUnmap` (:988-1010) and the destroy detach (:1244-1249) unchanged — they already handle the parent-dies-after-link case.
- Test: new wire test "set_parent to an unmapped toplevel clears the parent (X03)": create toplevels A and B, commit neither; `a.setParent(b)` → assert `t_a.parent == null` and `t_b.children.items.len == 0`. Then map B (commit → ack configure → attach buffer → commit), `a.setParent(b)` again → assert `t_a.parent == t_b`, `t_b.children.items[0] == t_a`. MUST also update the F16 test (:3561-3623): its first block sets `A.parent = B` with B unmapped and asserts the parent is stored, and its cycle block relies on stored parents — both must map A/B/C (commit + ack + buffer) before the parent/cycle assertions, else the new gate breaks them.
- Acceptance: parenting a dialog to a not-yet-mapped toplevel leaves the child parentless (transient/grouping behavior matches wlroots); parenting to a mapped toplevel stores the link and rejects cycles exactly as before.
- Risk: the F16 test rework is mandatory (two assertion blocks). No production caller depends on storing an unmapped parent (grep: only tests set `scheduled` state; main.zig never calls set_parent).

Layer-parented popups (`layer_parent`, L1) are not in the list — the topmost check is xdg-parent-only until F2 owns layer-popup stacking; document that in the field comment. F16-adjacent? No — toplevel `children` list is separate and untouched.

### X06 clear sent_payloads on unmap/reset [INFO] → FIX (Phase 2)
- Files: src/shell/xdg.zig — `resetConfigureState` at :369-374 (clears `sent_serials` at :373 but not role payloads; called from `unmapSurface` :433, `toplevelDestroy` :1239, `popupDestroy` :1402, and the NULL-buffer unmap hook `xdgSurfaceUnmap` :1918); `XdgToplevel.sent_payloads` field at :795, `XdgPopup.sent_payloads` at :1286. Reference: wlroots wlr_xdg_surface.c:31-42 destroys the whole `configure_list` in `reset_xdg_surface`.
- Change: in `resetConfigureState`, after `sent_serials.clearRetainingCapacity()` (:373), add `if (xdg.toplevel) |t| t.sent_payloads.clearRetainingCapacity();` and `if (xdg.popup) |p| p.sent_payloads.clearRetainingCapacity();`. This single choke point covers all four reset paths (unmap via role destroy, unmap via NULL buffer, and both role-object destroys — the destroy paths call reset explicitly at :1239/:1402 because `unmapSurface` early-returns on unmapped). Clear-not-deinit is correct: the subsequent `sent_payloads.deinit` calls (toplevelDestroy :1252, popupDestroy :1404) are no-ops on an empty list, and re-allocation is avoided across remap cycles (matches wlroots' destroy-and-realloc behavior with less churn).
- Test: extend "unmap via null buffer resets the configure state machine" (:2540): after configure + ack + a second configure (two payloads) then NULL-buffer commit, assert `ts.shell.?.toplevels.items[0].sent_payloads.items.len == 0` and `sent_serials.items.len == 0`. Also assert in "role-object destroy before map resets the configure machine (F8)" (:3231) that the destroyed role's payload list is empty post-destroy (observe via a fresh role on the same surface: no stale payload survives).
- Acceptance: ack-relevant and memory-relevant configure state both reset on unmap/reset; a stale payload can never be matched by a future ack even if serials are reused after wrap.
- Risk: none observed — serials were already cleared, so this only removes dead payload memory; the clear-before-deinit ordering is already compatible with the destroy paths.

### X07 configure_bounds / wm_capabilities flag-driven sends [MINOR] → FIX (Phase 2)
- Files: src/shell/xdg.zig — `XdgToplevel.configure` at :842-902 (bounds guard+send at :848-853, caps guard+send at :857-870); fields `scheduled.bounds_width/height` :749-750, `scheduled.wm_capabilities` :751-754, `wm_capabilities_sent` :805, `last_wm_capabilities` :808, `sent_bounds` :811; role-creation seed at :510-514. Tests driving the old API directly: "xdg toplevel configure/ack roundtrip" :2393-2396 (`t.scheduled.bounds_width = 1000` …) and "wm_capabilities and configure_bounds version gating (F4)" :3221-3224. Reference: wlroots wlr_xdg_toplevel.c:36-47 sends configure_bounds iff `configure->fields & WLR_XDG_TOPLEVEL_CONFIGURE_BOUNDS` (version-gated), :44-63 sends wm_capabilities iff the WM_CAPABILITIES bit is set — empty caps or explicit 0,0 bounds are legal sendable payloads; the compositor arms the bit per configure.
- Change: introduce a 2-bit `fields` mask (packed struct or `u2` enum set) on `XdgToplevel` beside `scheduled`; add `pub fn setConfigureBounds(t: *XdgToplevel, w: i32, h: i32) void` (writes `scheduled.bounds_width/height` + arms the bit) and `pub fn setWmCapabilities(t: *XdgToplevel, caps: WmCapabilities) void` (writes `scheduled.wm_capabilities` + arms the bit). `configure()` sends configure_bounds when the bit is set and `version >= 4`, and wm_capabilities (including an empty array) when the bit is set and `version >= 5`, clearing each bit after send. Replace the value guards (`!= 0,0`, `!isEmpty()`, change-vs-`sent_bounds`/`last_wm_capabilities` dedup) with the bit test; delete `wm_capabilities_sent`, `last_wm_capabilities`, `sent_bounds` (:805-811). Re-seed the role-creation default (:510-514) through `setWmCapabilities` so the first configure still announces the default set.
- Test: update the two existing tests (:2393-2396, :3221-3224) to call `t.setConfigureBounds(...)` instead of poking `scheduled` directly. New wire test "empty wm_capabilities is a legal sendable payload (X07)": v5+ toplevel, `t.setWmCapabilities(.{})`, `t.configure(0, 0)` → assert the client receives a wm_capabilities event with a zero-length array (`caps_count == 1`, payload empty); likewise `t.setConfigureBounds(0, 0)` → configure_bounds with 0,0 arrives. Assert re-arm semantics: configure twice with the bit set once → one event.
- Acceptance: a compositor can advertise "no capabilities" or explicit 0,0 bounds; event emission is compositor-requested (flag) rather than value-derived, matching wlroots.
- Risk: the F4 version-gating test (:3201) and the roundtrip test (:2332) touch bounds/caps — both must be migrated to the setter API in the same change (grep shows no production caller sets `scheduled.bounds_*` or `scheduled.wm_capabilities` outside xdg.zig, so the migration surface is tests only). Dropping the dedup fields changes behavior only for repeated identical sends — that is the intended wlroots semantics.
